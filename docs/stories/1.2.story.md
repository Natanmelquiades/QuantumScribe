## User Story

**Como** responsável por release e distribuição do QuantumScribe,  
**Quero** separar o Core CPU das dependências de build, teste e componentes opcionais,
com builds limpos e verificáveis,  
**Para que** o usuário receba uma instalação menor, funcional offline e sem CUDA,
Torch, modelos ou downloads silenciosos.

## Contexto e valor

Esta é a segunda story do `EPIC-QSAUDIT` e depende da Story 1.1, que está `Done` com
contratos e regressão protegidos. A auditoria identificou um bundle PyInstaller
temporário de aproximadamente 333,8 MB e 1.434 arquivos, além de
`requirements-common.txt` misturando `noisereduce`, SciPy e ONNX Runtime com o
fluxo essencial. Os locks CPU e CUDA atuais são derivados de um manifesto comum, o
build Linux instala um manifesto não travado e o workflow de release já referencia
artefatos opcionais cujo script de build precisa ser validado.

O objetivo é tornar o caminho de release mensurável e reproduzível. O Core deve
continuar local/offline, usar `device="auto"` e `compute_type="auto"`, preservar o
fallback CPU e não embutir modelos ou runtimes opcionais. A story não deve introduzir
uma nova UI, mudar o fluxo de onboarding ou extrair responsabilidades de `app.py`.

## Acceptance Criteria

1. Os manifestos separam dependências diretas do Core, build, testes e componentes
   opcionais; o lock do Core e os locks de build/teste aplicáveis possuem versões
   exatas e hashes verificáveis.
2. Um build limpo do Core para Windows produz artefato de no máximo 250 MB e não
   contém diretórios ou arquivos de `nvidia`, `torch`, `torchaudio`, `silero_vad`,
   modelos Whisper, nem bibliotecas opcionais removidas do Core sem justificativa
   de benchmark.
3. Builds Windows e Linux começam em ambientes limpos, instalam somente os perfis
   necessários com verificação de hashes e não dependem de `pip install` sem lock
   no caminho de release.
4. O Core abre em instalação limpa sem rede, não inclui modelo Whisper e não inicia
   download de modelo ou componente antes de uma ação explícita do usuário.
5. Artefatos opcionais, quando gerados, ficam fora do Core, são versionados e
   verificáveis por manifesto/SHA-256, e o processo de build não instala componentes
   via `pip` na máquina final.
6. O inventário de cada artefato registra caminho relativo, tamanho, hash e lista de
   itens proibidos encontrados; o mesmo input de build produz um relatório
   reproduzível e falha quando o Core viola a política.
7. O workflow de release mantém Actions fixadas por SHA, executa validação antes
   da publicação, gera checksums e consome apenas artefatos validados; falhas de
   testes, auditoria, inventário ou bundle bloqueiam a publicação.
8. `device="auto"`, `compute_type="auto"`, detecção automática de hardware e
   fallback GPU → CPU permanecem compatíveis, sem exigir GPU, CUDA ou driver para
   o caminho CPU.
9. A suíte de regressão, testes de manifestos/imports, smoke tests de build e
   inventário passam sem reduzir a baseline protegida pela Story 1.1.
10. `ruff`, compilação Python, `pip check` e `pip-audit` passam nos perfis aplicáveis;
    nenhum segredo, modelo ou dado pessoal é introduzido nos artefatos ou logs.

## Scope

### Incluído

- Auditar imports efetivos e declarar dependências diretas em
  `requirements-core.in`, com lock equivalente e hashes.
- Reorganizar os manifestos/locks de runtime, build, teste e componentes sem
  quebrar os aliases de instalação existentes sem uma migração explícita.
- Ajustar `QuantumScribe.spec`, `QuantumScribe-Linux.spec`, `build.ps1` e
  `build_linux.sh` para build limpo do Core com lock e verificação de tamanho.
- Completar e testar o processo de geração dos artefatos opcionais já referenciados
  pelo workflow, mantendo-os fora do Core.
- Criar ou ajustar o relatório de inventário de bundle/componentes e seus testes.
- Endurecer `.github/workflows/release.yml` para validação, checksums e publicação
  de artefatos previamente validados.
- Adicionar testes determinísticos de manifestos, imports, política do Core,
  inventário, build smoke e ausência de download em instalação limpa.

### Fora de escopo

- Criar onboarding, manifesto de modelos ou nova UI de recursos opcionais.
- Implementar o gerenciador completo de componentes, reinício controlado ou telas
  de instalação/remoção.
- Remover a função de backup/restauração ou alterar a experiência das configurações;
  isso exige story própria e revisão de impacto.
- Refatorar `app.py`, `settings_ui.py`, `stream_transcriber.py` ou criar
  `session_controller.py`.
- Instalar/atualizar drivers NVIDIA, reiniciar o Windows ou fazer downloads reais
  durante testes.
- Reparar o histórico Git, tomar posse do checkout ou executar push/PR remoto.
- Embutir modelos Whisper, Torch, CUDA ou credenciais nos artefatos.

  `localwhisper/stream_transcriber.py` e `localwhisper/transcriber.py`: consumidores
  cujo fallback e import boundary devem ser protegidos. [Source: architecture.md#5.2 Existing and Target Boundaries]

### Regras técnicas

- Não adicionar framework novo. Usar Python já suportado (`>=3.11,<3.14`), Pytest,
  Ruff, PyInstaller, PowerShell, Bash e locks existentes. [Source: architecture.md#3.2 New Technology Additions]
- O Core não pode depender de CUDA/Torch/modelos e não deve importar componentes
  opcionais apenas para descobrir disponibilidade. [Source: architecture.md#5.1 Architectural Principles]
- Builds devem iniciar limpos, executar lint/testes/compilação/auditoria antes de
  criar o artefato e permitir rollback para o artefato anterior conhecido como bom.
  [Source: architecture.md#9.2 Enhancement Deployment Strategy]
- Download, extração e promoção de componentes devem preservar staging, hash,
  compatibilidade, limites e path traversal protection. [Source: architecture.md#7.2 Failure Handling]
- Logs de build e runtime não devem conter áudio, texto ditado, tokens, segredos ou
  caminhos pessoais completos. [Source: architecture.md#10.3 Critical Integration Rules]
- O limite de 250 MB, ausência de CUDA/Torch/modelos, instalação offline e separação
  de perfis são requisitos do produto; não reduzir o critério para acomodar um build
  pesado. [Source: PRD_CORE_LEVE_COMPONENTES_SOB_DEMANDA.md#18 Release]
